## 1. 理解系统的基本分工

Globex 是一个用自然语言交互的商品选购系统。用户说用途、预算和收货地，系统理解需求、查找商品、解释差异，并在用户批准后保存购买意向。

例如，用户说：“我想买一个通勤背包，轻便一点，预算三百元，寄到中国。”

这里的工作不只包括生成一段回答。系统还要把“通勤”和“轻便”转成检索条件，处理预算与配送限制，查询真实存在于商品目录中的规格，并把结果显示成可以继续操作的商品卡。

整个系统存在三种决策权。

**模型决定下一步尝试做什么。** 它理解语言，选择工具，组织推荐理由，判断是否需要补充信息。

**业务系统决定什么操作合法、哪些事实可靠。** 它查询商品、过滤条件、核对身份、计算金额和提交数据库事务。

**用户决定是否批准需要授权的动作。** 模型建议购买、准备确认单，和用户批准执行，是不同阶段。

这套分工的目的，是让自然语言交互具有灵活性，同时把身份、库存、金额和授权放在确定性机制中。模型可能理解错一句话，但不能因此自行创造一个商品、假装用户已经批准，或者绕过数据库库存限制。

当前项目的商品来自样例目录，订单是本地购买意向账本。系统尚未连接真实支付、发货与物流。文中的“下单”应理解为确认并保存本地购买意向，不能理解为真实商家已经收款或安排配送。

## 2. 整体架构为什么分成几层

### 2.1 用户界面层

这一层直接面向用户，负责输入、回复、商品卡、规格详情、比较、收藏、订单、表单和审批按钮。

它处理的是交互问题：用户现在看见什么、可以点击什么、操作是否正在进行、是否需要等待确认。

界面不拥有最终业务事实。某张卡显示“待确认”，不意味着订单已经创建；用户点击“批准”，也不意味着执行一定成功。最终状态要由服务端返回。

### 2.2 请求接入层

这一层接收浏览器请求，检查请求格式、买家身份和会话归属，再把有效请求交给内部服务。

它还负责把执行结果按约定的协议传回浏览器。无论内部使用哪种模型或存储，页面都应该接收到相对稳定的事件和业务数据。

### 2.3 应用编排层

这一层把一次需求组织成完整任务。它恢复会话、准备模型上下文、加载偏好、启动 Agent、处理错误并保存结果。

其中一部分是确定性编排：每轮都必须核对身份和保存状态。另一部分是模型驱动的规划：这次先搜索，还是先澄清，是否需要专家子任务。

把两者分开，是为了避免让模型负责“记得保存”“记得检查买家归属”这类基础保障。

### 2.4 领域规则层

这一层表达商品、规格、金额、地址和订单，以及这些对象必须满足的规则。

例如数量必须合法，同一订单的金额不能随意混合币种，只有允许的订单状态才能取消。这些规则不应因为换了模型或网页样式就改变。

### 2.5 基础设施层

这一层实现模型调用、数据库读写、向量检索、缓存、消息队列和追踪。

它把抽象能力变成具体技术。例如“读取商品”可以由本地目录实现，“保存订单”可以由数据库实现，“查找语义相关候选”可以由向量检索实现。

### 2.6 分层的收益和成本

分层使组件能够围绕清晰职责替换和测试。未来商品源改成商家接口，检索服务仍可以接收相同的查询条件；模型更换时，用户确认和库存事务不必跟着改变。

代价是一次请求经过多个组件，需要维护接口、数据合同和版本。项目采用了这种分层思路，但部分组件之间仍有直接耦合，不能认为分了目录就已经彻底实现所有依赖隔离。

## 3. 用一个例子走完整条链路

### 3.1 第一轮：提出选购需求

用户输入：“三百元以内，找一个寄到中国的轻便通勤背包。”

浏览器将这条消息加入当前对话，创建本轮运行标识，并向服务端发送请求。请求还带有当前会话、买家、语言和币种等信息。

服务端检查输入是否有效、当前身份是否有权使用这个会话，然后登记本轮运行。

接下来，编排器恢复服务端保存的会话状态，读取当前长期偏好、所选方案和交易状态。例如用户长期避免某类材质，这项约束会作为本轮参考进入上下文。

主 Agent 读取这些材料，决定调用商品检索工具。工具接收结构化条件，检索服务找到候选，过滤不满足预算、配送和材质限制的商品。

商品结果同时用于两个目的：供模型形成推荐理由，供页面显示结构化商品卡。它们来自同一批业务结果，但不是同一种展示形式。

执行过程中，文字、工具状态和商品事件陆续保存并传回页面。结束时，会话、对话和证据被保存，下一轮可以继续。

### 3.2 第二轮：继续核对商品

用户说：“第二个有什么规格？现在还有多少库存？”

系统利用之前候选的稳定顺序理解“第二个”，取得对应的商品标识，再精确核对规格和当前库存。

历史候选帮助识别对象，当前查询提供最新观察。不能因为上一轮有库存，就把旧数值当成这一轮的当前库存。

### 3.3 第三轮：准备购买意向

用户说想购买某个规格，并提供数量和收货信息。

系统核对商品是否曾在这个买家的这个会话中被检索返回，再核对规格、数量、地址和库存。如果信息不足，就请求补充；齐全后生成确认卡。

此时尚未创建订单，也没有扣库存。

只有用户点击批准，服务端才检查确认快照和有效期，在数据库事务中创建购买意向并扣减库存。页面根据保存后的结果展示终态。

### 3.4 为什么要区分轮次、会话和调用

会话是一段多轮选购；一轮运行是用户一次发送或一次接续；一次模型调用只是这轮运行中的一个步骤。

一轮可能包含几次模型调用和多次工具调用。因此，排查错误和统计消耗时，不能只看“用户发了几条消息”。

## 4. 前端怎样把执行过程变成页面

### 4.1 页面组件只负责各自的交互

输入组件处理文本和方案选择；商品卡处理概览、收藏、比较和详情；订单表单收集规格、数量和地址；交易确认卡展示用户将批准的操作。

长期资料工作区管理偏好和个人方案；模型工作区管理连接和选择；上下文工作区展示容量和整理结果；历史组件负责恢复与搜索旧会话。

执行记录组件显示工具步骤、等待确认和完成状态。思考展示只使用供应商公开返回的思考内容，系统不会补造未返回的推理过程。

这些组件分开，能够让每种用户动作有明确的数据输入和回调，而不是让一个页面同时解析所有协议和业务细节。

### 4.2 客户端控制器负责状态协调

页面背后有一个客户端控制器，统一管理消息、当前运行、商品、确认、审批、历史和网络状态。

React 页面订阅它的快照。当回复增加了文字或商品列表发生变化，控制器更新快照，页面重新渲染。

它还封装服务端请求与恢复逻辑，使组件不用各自处理事件游标和网络重试。代价是控制器的职责较多，后续扩展时要避免变成难以维护的大型状态中心。

### 4.3 文字与业务数据分开展示

模型文字适合说明“为什么推荐这个包”。商品卡则需要稳定的商品、规格、价格、币种和库存字段。

如果从文字中猜价格，就可能遇到格式改变、多个价格混在一起、币种缺失或模型写错。项目因此直接使用服务端返回的结构化商品数据展示卡片。

这能保证卡片字段有业务来源，但并不意味着模型的每一句推荐理由都自动正确。回答和事实仍需要分别评估。

### 4.4 历史、收藏和比较各有什么作用

历史保存选购过程与商品批次，帮助用户继续上一段任务。收藏保存买家挑中的商品快照，方便回看。比较把不同商品的结构化属性放在一起展示差异。

它们都不能替代当前交易核验。收藏中有一件商品，不代表现在仍有同样的价格和库存；历史卡片也不是永久有效的报价。

浏览器缓存用于加快页面恢复，服务端记录是更可靠的恢复来源。浏览器缓存丢失，不应被理解为所有业务历史已经丢失。

## 5. 请求入口与身份校验

### 5.1 入口先检查什么

服务端先检查请求是不是支持的格式、用户文本是否为空、会话和运行标识是否有效，再检查买家身份与会话归属。

随后才进入 Agent 执行。这样能够尽早拒绝无效请求，避免为格式错误或无权限请求支付模型调用成本。

### 5.2 为什么不能相信浏览器发来的历史

浏览器可以展示历史，也会随请求携带部分消息，但这些内容不能覆盖服务端保存的事实。

如果允许浏览器直接改写历史状态，用户或错误客户端就可能将“待确认”改成“已批准”，或者伪造某个商品曾被检索过。

因此，服务端提取当前用户输入，并从自己的持久记录恢复工作状态。客户端展示内容和服务端事实有不同可信度。

### 5.3 资源标识不等于权限

知道一个订单号，只能说明知道它的名字，不能证明有权读取它。订单、会话、表单、记忆和工具证据都要绑定买家范围。

项目提供便于本机体验的演示身份，也提供签名身份模式。签名模式验证令牌是否由可信方签发、是否用于当前系统、是否过期，并把签名主体与请求中的买家对应起来。

演示身份不是完整的生产登录系统。会话归属检查和可信身份认证也不是同一件事：前者保护资源范围，后者确认请求者是谁。

## 6. 事件协议与断线恢复

### 6.1 为什么回复要分批传回来

Agent 可能进行多次查询。如果必须等所有步骤完成才返回，用户只能看见长时间等待，无法判断系统是否还在工作。

项目使用 SSE，即服务端发送事件的流式传输方式。浏览器提交一次运行请求，服务端持续发送文字、工具步骤、商品数据和结束事件。

SSE 主要负责服务端向浏览器传输。用户补条件、批准或拒绝，则通过新的请求表达。

### 6.2 AG-UI 解决什么问题

AG-UI 是 Agent 与界面之间的事件协议，规定运行开始、文本变化、工具调用、状态快照和结束等事件如何表达。

内部 Agent 框架的事件不完全等于页面需要的事件，因此存在一个协议适配组件：它把内部事件和业务事件转换为界面可以消费的形式。

有了统一协议，页面不必依赖某个模型供应商的原始响应格式。官方客户端处理协议状态，项目补充商品、审批和执行记录等业务映射。

### 6.3 为什么事件先保存，再展示

如果事件只通过网络发送，断线期间的进度就无法恢复。项目把事件按序号写入持久运行日志，浏览器再读取这些日志。

例如浏览器收到第六十条事件后断线，重连时说明从这之后继续接收。客户端还检查重复和序号缺口，避免同一段文字追加两次，或悄悄漏掉某张确认卡。

这套机制增加数据库写入和日志存储，但让“用户看到过什么”和“运行保存了什么”更容易核对。

### 6.4 恢复订阅与重新执行不同

网络中断时，原运行可能还在服务端继续。客户端恢复的是已有日志，不会简单地再次发送用户输入并启动第二轮。

重新执行会增加模型费用，还可能重复准备操作。将运行生产和网络订阅分开，正是为了避免这种混淆。

用户点击停止，则会明确请求服务端取消运行。项目正式页面的运行不依赖单个网络订阅存活；旧的兼容流调用存在不同取消行为，不能混为一谈。

### 6.5 服务重启能恢复到什么程度

服务重启后可以保留已保存的事件、会话和中断事实，并检查过期运行。

这不是把模型计算从某一个 token 无缝搬到新进程。系统不能保证从任意计算瞬间继续，更不能为了恢复自动重放交易。

## 7. 会话管理与编排器

### 7.1 会话保存哪些东西

会话保存模型已经读过的消息、工具结果、摘要、计划和待审批状态，使下一轮不必从零开始。

完整页面历史与模型工作状态并不完全相同。页面可能保留所有可见聊天和商品批次，而模型只带当前需要的部分上下文。

会话管理组件从持久记录恢复状态，必要时创建新的 Agent，并把本轮使用的模型配置和规则版本绑定进去。

### 7.2 编排器负责哪些确定性步骤

每轮开始，编排器取得会话执行权，设置当前买家和会话环境，加载相关资料，再启动主 Agent。

执行时，它消费模型和工具事件，关联业务结果，处理可以重试的故障，并把错误转换成用户能够理解的结果。

结束时，它保存工作状态、对话和证据，记录本轮用量，清理本轮临时运行信息。

这些职责需要每次可靠发生，不能依靠模型临时想起。

### 7.3 为什么使用协程上下文

工具和子任务需要知道当前买家、会话、币种和模型版本，但不应该让模型在每次工具参数中自行填写这些身份信息。

项目使用协程级上下文携带这类信息。不同并发请求有各自的上下文，子协程可以继承所属请求的环境。

这样减少参数传递，也降低“模型把另一个买家标识填进工具”的风险。继承的是运行环境，不是自动继承主 Agent 的全部对话记忆。

### 7.4 最新事实优先于历史摘要

编排器每轮重新读取当前偏好和交易状态。过去摘要里说用户喜欢蓝色，但用户已经删除了这条偏好，就不能继续把旧摘要当作现行偏好。

同样，历史中有待确认单，也不能直接视作已经创建订单。当前持久账本决定交易现状，历史只用于理解过程。

## 8. 主 Agent 怎样决定下一步

### 8.1 Agent 与普通聊天的区别

普通聊天通常是把输入交给模型，然后显示回答。Agent 还能够提出工具调用请求，获得外部结果，再根据结果继续处理任务。

主 Agent 每次读取用户需求、工作上下文、规则和工具说明，决定直接回复、查询、补条件、建立计划，或者派发子任务。

项目使用 AgentScope 承担执行循环与事件机制。模型选择动作，框架负责调用工具并把结果送回下一次模型输入。

### 8.2 工具循环如何推进

仍以选购背包为例：第一次模型调用可能提出搜索请求；搜索返回候选后，第二次模型调用可能直接推荐，也可能发现缺少重量信息而继续核验。

因此，一轮用户输入不对应固定数量的模型调用。具体步骤取决于需求清晰程度、工具结果和模型判断。

这里的“判断”不意味着系统能够看见模型全部内部思考。能够可靠观察的是它发出的请求、公开返回的内容和工具结果。

### 8.3 为什么有计划管理

复杂需求可能包含比较多个品类、核对属性、计算报价和准备购买意向。任务清单帮助模型记录哪些已经完成、哪些仍需处理。

计划是工作组织手段，不是执行成功证明。任务被标成完成，仍要有对应业务结果支持。

简单检索不需要先建立庞大计划，否则只是增加调用和等待。

### 8.4 如何结束循环

模型给出最终回复、等待用户审批、遇到错误或达到步数上限，都可能结束一轮。

当前主 Agent 的执行步数上限为十五步，专家子 Agent 为六步。这些数字限制执行过程，不能直接解释为最多十五次所有类型的模型请求，也不能代替成本预算。

另外，重复检测和预算控制会约束没有进展的工具调用，避免一直重新搜索同一个空结果。

## 9. 子 Agent 为什么按需使用

### 9.1 检索专家和交易专家各做什么

检索专家负责一段独立的商品搜索、候选筛选或知识辅助任务。交易专家负责在既有授权边界内核对和准备交易相关操作。

主 Agent 本身也拥有这些业务工具。因此一次简单搜索、查单或准备确认可以直接完成，不必额外找一个专家模型转述任务。

### 9.2 什么时候派发更合适

如果任务能分成彼此独立的部分，例如同时查背包和耳机，多个专家可以并行处理。

如果子任务会产生大量候选和反复筛选，独立上下文可以避免这些中间数据占满主对话。

如果某段任务内部需要多轮工具往返，交给专家处理也能让主 Agent 只接收压缩后的结论与证据。

### 9.3 上下文隔离如何实现

每次派发创建独立的专家工作状态。它只收到任务说明以及服务端补充的相关资料，看不到主 Agent 的完整聊天历史。

因此任务说明必须自包含：具体目标、预算、需要核对的商品和必要条件都要交代清楚。

检索专家的长期偏好由服务端额外补充，降低主 Agent 漏抄偏好的风险。交易专家不靠偏好自行挑选新商品，而应核对任务给出的商品和规格。

### 9.4 并行为什么不是免费的

并行降低独立任务的等待时间，却不会自动减少模型总调用量。它还可能同时占用更多网关名额和共享预算。

多 Agent 也存在交接损失：主 Agent 的约束没写全，专家就可能执行偏差。因此专家返回的结果带有证据引用和核实过的商品标识；未经核实的标识需要进一步核验。

多 Agent 是控制任务复杂度的方法，其效果需要评测，不能仅根据“用了几个 Agent”判断系统更好。

## 10. 工具与业务服务怎样分工

### 10.1 工具是一份受限能力合同

模型可以选择工具，但工具需要预先说明名称、用途、接受哪些参数、返回什么结果。

例如搜索工具接受品类、收货国和价格上限；订单准备工具接受商品、规格、数量和收货信息。模型不能因此获得任意数据库操作或执行任意脚本的能力。

参数进入系统后仍要做类型、范围、身份和业务条件检查。模型给出看起来合理的参数，只代表提出请求，不代表已经合法。

### 10.2 为什么工具后面还有业务服务

工具负责把模型参数转换成内部业务输入，取得当前身份，发布执行事件，并把结果包装成模型能读取的形式。

业务服务负责实际动作，例如检索候选、核对地址、准备确认或查询订单。存储组件负责读写数据库或目录。

这样的分工使页面按钮和 Agent 工具能够共用业务规则。用户从订单页面发起取消，不必让模型再理解一遍，仍然能够经过相同的确认服务。

### 10.3 澄清工具有什么特殊之处

缺少真正影响选择的条件时，Agent 可以生成结构化澄清表单，决定问题文字、选项、顺序和是否必填。

前端依据表单结构渲染，而不是固定追加预算、旅行或其他问题。服务端保存表单，使刷新后仍能恢复。

Agent 应结束这一轮等待用户填写。未提交的答案不能成为搜索条件，更不能被当作记忆或交易批准。

### 10.4 工具结果为什么有多种形态

完整业务结果包含价格、规格、条件、观察时间和证据。页面需要其中的展示字段，模型可能只需要决策字段，历史核验则可能需要完整原始结果。

因此项目区分原始证据、模型决策投影和页面状态。它们应有共同来源，但不必包含完全相同的内容。

## 11. 商品数据和检索系统

### 11.1 商品主数据、库存和向量索引

商品名称、描述、规格和目录价格保存在版本化本地样例目录中，启动后加载到内存商品仓储。

库存另外保存在持久交易账本中。查询商品时，会读取账本中的当前库存，以反映已经发生的购买意向和取消。

向量索引保存用于语义检索的数值表示和索引信息。搜索得到商品标识后，再读取商品仓储获得完整事实。

这里不能说“商品全部存在本地数据库”，也不能说“向量库就是全部商品事实的来源”。三种存储分别承担目录、交易状态和语义定位。

### 11.2 Embedding 为什么能够处理口语需求

Embedding 把文字转换成一组数值，使语义相近的文字通常在数值空间里更接近。

用户说“抗造”，商品描述可能说“结实耐用”；如果只找字面相同词，容易漏掉。语义向量可以帮助找到这种措辞不同但意思接近的候选。

项目分别为商品可搜索文本和用户检索词生成向量，使用 Qdrant 按相似度寻找候选。

向量相近只意味着语言内容相关，不代表预算、库存和配送都符合，也不能证明某个未检索到的商品不存在。

### 11.3 为什么建索引和搜索分开

建索引时，系统批量处理商品描述并保存向量。用户搜索时，只需要计算查询向量并读取已有索引。

如果每次请求重新计算全部商品向量，成本和延迟会随商品数增长。项目通过内容指纹和嵌入身份判断哪些商品缺失或变化，只重新计算必要部分。

批次逐个保存，某批失败不必让所有已完成批次作废。模型、文本或维度变化时，旧向量不能无条件复用。

### 11.4 召回和精排分别优化什么

召回先从商品库中找出一批可能相关的候选，重点是不要漏掉真正合适的商品。

精排再把用户需求和候选描述一起交给专门排序服务，判断谁更匹配。它重点处理前几名的次序。

向量检索适合快速找候选，精排能进行更细的文本比较，但增加远端调用和延迟。候选阶段没找回的商品，精排也无法凭空补上。

### 11.5 硬约束由业务过滤执行

搜索服务检查是否有库存、品类是否匹配、能否配送到指定国家、材质是否违反排除要求、商品单价是否超出上限。

即使商品语义很接近，只要不能寄到收货地，也不应进入可选结果。

被排除的候选可以保留原因，帮助模型解释“有这个商品，但它超出预算”，而不是把所有空结果都说成“库里没有”。

当前价格上限过滤的是目标币种中的商品单价，并不自动处理多件含运税的总预算。这个口径必须向用户说明。

### 11.6 精确查询为什么绕过语义匹配

用户给出明确商品或规格标识时，系统可以直接核对目录。这样能够准确回答是否存在这个对象、有哪些规格和当前库存。

语义搜索只返回相关候选的前若干名。没有出现在这些候选中，不等于商品不存在，因此存在性判断应由精确目录查询完成。

### 11.7 检索失败如何降级

精排不可用时，可以保留向量排序；向量查询异常或没有候选时，可以使用关键词搜索。

关键词搜索采用分词和中文相邻字符组合，成本低，但不如语义向量擅长理解口语同义表达。

项目还实现了可选的混合检索：把关键词排名和向量排名融合。按排名融合能够缓解两种原始分数尺度不同的问题。不过该候选默认关闭，不能直接认为已经证明效果更好。

## 12. 知识库与 RAG 的工作原理

### 12.1 知识库回答什么

商品检索回答“有哪些可选商品”；知识库回答“怎样挑选、怎样理解属性、有哪些避坑原则”。

例如用户问背包怎样挑，知识库可以提供背负、容量和材质判断资料。它不能仅凭一篇选购文章证明某个商品有货。

项目将商品索引与品类知识索引分开，避免文章片段和商品候选混在一起。

### 12.2 文档为什么需要切块

一份资料可能同时讨论多个品类或多个话题。整篇存成一条记录，会让无关内容影响相关度，也增加送给模型的文字量。

系统先读取知识文档，按长度与内容切成片段，为片段建立向量。查询时找到相关片段，将它们作为回答材料。

片段太小可能丢掉条件，太大可能掺入无关内容，切块本身也是质量取舍。

### 12.3 RAG 中检索和生成如何配合

RAG 即检索增强生成。模型先通过工具取得外部材料，再用材料回答。

它减少了完全依赖模型记忆的风险，也让事实来源可追踪。商品检索后生成推荐属于广义检索增强，知识文档检索后回答属于典型文档 RAG。

RAG 并不保证正确。如果检索到了错误资料、资料过期，或者模型忽略适用条件，答案仍会出错。

### 12.4 为什么最近的片段也可能不能回答

向量搜索通常会找到某些最近结果，但所有资料都不相关时，“最近”仍可能很不相关。

项目检查相关性和资料资格。涉及政策的信息，还需要考虑来源、有效日期和适用条件；合成评测资料不能冒充确定政策事实。

资料不足时应说明未知或需要核验，而不是把检索结果硬拼成答案。

### 12.5 联网搜索的作用与限制

配置了相应服务后，Agent 可以联网查知识库没有覆盖的时效信息。

联网扩大了资料范围，也引入了不可信网页内容和额外延迟。页面正文中的指令不能因此变成系统命令，仍需要经过权限和内容处理。

订单查询和数据库交易本身不需要文档 RAG。它们需要读取或修改精确业务状态。

## 13. 价格规格与订单规则

### 13.1 为什么商品和规格分开

一款背包可能有不同颜色和容量。商品表示这款产品，规格表示具体可购买单元。

订单和库存需要关联具体规格，因为不同规格可能有不同价格和库存。用户选商品不意味着系统可以自行决定任意规格。

默认规格也应来自已展示的检索结果，并在确认卡上明确显示。

### 13.2 金额为什么不用任意小数相加

项目用整数最小单位保存金额，并明确币种。这样可以减少浮点运算造成的小数误差，并检查相加的币种是否一致。

例如两个数值都写成一百，如果一个是人民币、另一个是美元，就不能直接合成二百。

当前演示把支持的币种统一按百分之一单位换算，尚未完整处理每种货币的实际小数位规则。这是演示简化，不应当作完整金融金额体系。

### 13.3 汇率和运税由谁计算

价格转换和运税使用本地规则组件。它们读取金额、品类、收货地和数量，返回有明细的报价，模型解释结果而不自行换算或估税。

当前规则和汇率是演示数据，不能代表实时汇率、现行法规或商家的最终收费。

商品单价、单件到手价和订单确认金额也有不同含义。检索卡可以显示单件商品加运税的报价；当前订单确认金额只包括商品金额，不能说已经支付这份到手价。

### 13.4 订单状态为什么必须受限制

订单包含明细、数量、地址、币种和状态。它至少要有一条有效明细，同一订单不能混算不同币种。

只有允许取消的状态才能取消，并需要取消原因。用户点击按钮或模型请求取消，都不能跳过这些条件。

这些不变量可以在没有真实模型的情况下验证，确保基础业务规则不随模型回答变化。

## 14. 长期记忆为什么不是聊天历史

### 14.1 三种信息的有效期不同

“这次要蓝色”是一次任务条件；“记住我喜欢蓝色”可能是长期偏好；“这个蓝色背包很适合你”只是助手的推荐判断。

如果把三种信息都存成长期事实，下一次买别的商品时就可能错误沿用临时要求，或者把模型判断变成用户自己表达过的偏好。

项目只在用户明确保存或通过批准的记忆工具表达变更时，写入长期记忆。

### 14.2 为什么写入前先提炼

用户表达可能包含寒暄、情绪、原因、临时预算或个人信息。原样保存会让记忆冗长，并混入不稳定内容。

提炼组件使用模型抽取简短、稳定、独立的偏好。系统继续检查原文证据、长度、类别和冲突关系，确保生成事实有输入依据。

提炼本身也会失败。项目不会在提炼不可用时，把未经处理的原文悄悄记成成功偏好。这提高了事实质量要求，也增加了模型调用、等待和保存失败的可能。

### 14.3 事实和向量为什么一起保存

规范化偏好用于展示和解释，偏好向量用于按本轮需求召回。

如果分别保存，可能出现偏好已经删除但向量还存在，或者文字改了而向量没更新。项目把两者放在同一条持久记录中，原子提交。

个人偏好规模较小，可以在本地数据库保存向量并计算余弦相似度，不必另开一套向量服务。

### 14.4 正向与负向偏好为什么处理不同

正向偏好通常是排序参考。例如用户喜欢小众设计，但不是每次买电池都需要强调它。因此只召回与本轮需求相关的部分。

负向偏好可能是硬约束，例如避免某种材质，不应因相关度排名较低就被遗漏。项目保留全部当前负向偏好。

有明确结构化映射的材质排除可以进入检索过滤；其他自然语言负向约束仍需要模型遵守，不能声称所有偏好都已经自动转成确定性过滤。

语义召回失败时，项目保留负向约束，并明确降级，不假装正向偏好仍成功命中。

### 14.5 修改和删除为什么检查版本

用户可能在页面修改偏好，同时 Agent 仍拿着之前的记录。若只靠名字修改，就可能覆盖或删除刚更新的内容。

每条记忆有稳定标识和版本。变更提交时说明自己依据哪个版本，服务端比较当前版本，不一致就拒绝旧操作并要求重新核对。

用户撤回的记忆不能从历史摘要中自动恢复。下一轮重读当前事实，是避免旧记忆复活的关键。

## 15. Skill 与提示词的区别

### 15.1 Skill 是可复用的方法资料

Skill 可以描述某类选购的处理步骤，例如先核对容量和尺寸，再比较重量、材质和价格。

它回答的是“这类任务怎样做”，而长期偏好回答的是“这个用户喜欢或避免什么”。

系统提示词规定 Agent 的总体职责和行为要求，工具合同规定它具体能够请求什么操作。这些也不等于用户编写的 Skill。

### 15.2 为什么先看目录，再加载正文

如果把所有方案全文放进每轮输入，模型会读很多无关内容，费用和干扰都增加。

项目先给出名称、描述和适用范围等目录信息，相关时才读取正文。用户明确选中方案时，服务端在首个模型调用前核验并加载指定版本。

这样降低无关上下文，同时让“选择了哪个方案”和“实际读了哪份内容”能够对应。

### 15.3 个人与公共资料怎样区分

个人 Skill 只属于当前买家。公共方案和策略需要可信操作员导入、审核和发布，并可能设定有效期和可用工具范围。

未发布、过期、撤回或版本不匹配的资料不能悄悄继续使用。用户上传的方法也不能提供任意脚本执行能力。

### 15.4 Skill 为什么不能免除审批

用户可以写“优先挑轻便商品”，但写“以后下单不用确认”不能改变服务端批准机制。

Skill 是参考资料，权限由系统决定。把资料内容和执行授权分开，能避免个人方案绕过交易与记忆审批。

### 15.5 版本和内容指纹分别有何作用

版本说明这是哪次修订，内容指纹绑定这次修订的具体内容。只看名字或版本标签，无法发现同名内容被替换。

会话绑定规则和工具合同版本，避免旧对话在不兼容的新规则下悄悄继续。必要时会提示另开会话，旧历史仍保存。

版本治理增加发布和维护工作，但让错误能够追溯，也降低历史资料与新事实混用的风险。

## 16. 长对话的上下文治理

### 16.1 模型上下文不是无限记忆

模型每次请求只能读取有限内容。系统提示、工具定义、聊天历史、商品结果、计划和摘要都会占用输入空间。

商品结果特别容易变大：多个候选、多个规格、长描述和报价明细不断累积，后续模型调用还可能反复读取它们。

直接把所有历史带进去，会增加延迟和费用，最终超过容量。简单删除又可能丢失预算变化、商品顺序和订单状态。

### 16.2 为什么保留三层信息

完整对话与商品批次用于用户回看；模型工作上下文用于下一步决策；原始工具证据用于精确核验和追溯。

三层用途不同，因此模型工作空间可以整理，而用户历史和完整证据继续保留。

例如一份很长的商品列表离开当前工作上下文后，可以保留引用；模型需要比较旧属性时再回查完整证据。

### 16.3 默认压缩怎样工作

基础压缩策略在上下文接近阈值时启动。项目配置的基础触发比例是窗口的百分之七十五，保留比例是百分之十五，但实际可用输入还要考虑输出和安全空间。

压缩先尝试归档较旧的大工具结果，再由框架决定是否需要模型摘要。

摘要要求保留任务目标、约束作用域、商品与规格、交易状态和待确认动作。摘要只是历史工作记录，不能取代当前账本或用户授权。

### 16.4 分层治理为什么保护未读结果

项目还提供可选分层治理方案。它记录哪些工具结果已经进入一次成功的模型响应过程，再决定哪些可以裁剪或归档。

如果搜索刚返回一批商品，模型还没读过，就先删去属性，它可能永远没有机会完成比较。

“先读后裁剪”保护新结果的首次使用机会；压力裁剪则在接近容量限制时进行整理。候选策略有质量与效率取舍，不能因为实现了就认为默认启用或已经证明收益。

### 16.5 回查为什么需要限额和分页

归档后，模型可以按证据引用、商品或字段取回历史事实。回查仍然有数量和容量限制。

如果一次把所有归档内容读回来，上下文又会立即膨胀。只读相关字段和必要页面，才能让回查真正服务于当前问题。

历史价格和当前价格必须区分。回查历史失败，不能重新查一个当前价格去填“上一轮价格”。

### 16.6 手动整理为什么有条件

用户可以查看当前占用和工作摘要，并申请整理。服务端检查运行状态和会话版本，建立可恢复的整理记录。

生成中或等待工具审批时不能随意整理，因为模型和待审批调用依赖现有状态；改变状态可能造成恢复不一致。

### 16.7 容量要预留什么

模型窗口并不全部属于输入。还要留出模型生成回答的空间和计数误差的安全空间，有些模型还声明独立输入上限。

工作上下文目标应取实际可用输入与项目目标之间较小的值。受保护内容仍装不下时，应请求缩小比较范围或分批处理，而不是删掉授权信息或自动重做交易。

## 17. 模型接入用量与缓存

### 17.1 模型注册中心管理什么

它统一管理模型连接、能力声明、窗口档位、思考选项、修订版本、用户显示偏好和默认选择。

密钥在服务端加密保存，页面拿到的是公开目录和配置结果。主密钥与数据库需要配套保留，否则加密凭据无法恢复。

添加连接时使用固定小探针，核对流式输出、工具调用及声明参数。这个探针不能证明最大窗口实际可用，也不能证明选购质量。

### 17.2 为什么执行时冻结模型配置

用户在生成过程中改模型，正在运行的一轮仍应完成原配置，新选择下一轮生效。

等待审批后恢复，也沿用产生审批的模型和参数。这样避免一次操作前后突然改变工具理解、窗口和思考设置。

切到更小窗口前要检查当前工作状态能否容纳，不能为了换模型直接清空必要上下文。

### 17.3 流式调用为什么需要完整生命周期

模型开始返回第一段文字时，远端计算和网络连接可能仍在继续。

共享并发名额必须占用到流结束或明确关闭。否则系统会认为一个调用已经结束，启动更多调用，实际并发超过网关限制。

取消、异常和未读取完的流都要释放资源。项目为多层流和底层连接设置统一关闭机制，减少泄漏。

### 17.4 重试、回退和续写有什么不同

重试是对短暂故障重新尝试，比如限流或连接失败；回退是在允许时换备用模型；续写是在受限条件下继续不完整回答。

它们都有次数、容量、预算和协议限制。取消或非法工具请求不应被当作普通故障一直重试。

有限续写是默认关闭的候选能力，并不重放业务工具。整轮重试与单次模型恢复也存在不同分支，不能统称为无限自动恢复。

### 17.5 估计占用、实际消耗与预算

上下文估计回答“下一次输入可能占多大空间”。供应商用量回答“这次请求实际报告消耗了多少”。预算账本回答“这一整轮累计用了多少、还允许花多少”。

三者不能互换。页面容量圆环不是累计账单；上一请求的输入用量也不等于追加回答后的当前工作占用。

项目优先保持模型身份与计数口径一致，在可信条件下使用本地分词与消息模板计数，否则明确采用保守估计和校准。供应商缺少实际用量时，未知不能记为零。

### 17.6 三种缓存为什么分开

嵌入缓存保存相同文本的向量，减少重复计算。键需要绑定嵌入身份，否则模型变化后会用错向量。

语义回答缓存寻找非常相近的首轮问题，复用最终文本。它需要隔离用户、偏好、模型与规则变化；当前网页不用这份缓存，因为只有最终文字无法恢复商品和确认事实。

提示词缓存则由供应商复用相同请求前缀的计算。项目默认不主动添加显式缓存标记，显式缓存和稳定前缀属于待验证候选。

稳定前缀减少不必要的输入变动，但不能仅凭本地估计证明缓存命中或费用下降。需要供应商实际用量、失败消耗和延迟证据。

## 18. 用户确认与可靠交易

### 18.1 为什么准备和执行必须分开

模型理解“我想买这个”后，可以准备一份具体意向，包括商品、规格、数量和收货信息。

用户需要看见这份明确内容，再批准或拒绝。模型知道用户想买，不等于用户已经核对并批准这一组参数。

因此交易准备工具只生成确认卡，批准动作通过独立用户接口执行。模型没有代用户批准的工具。

### 18.2 确认快照怎样绑定内容

服务端把将要执行的内容保存成快照，并计算内容指纹。用户批准时带上对应指纹。

这样服务端可以验证批准的是同一份商品、规格、数量和地址，而不是确认卡展示之后被改变的内容。

确认还绑定买家、会话、操作标识和有效期。过期或不匹配时需要重新核对。

### 18.3 商品证据为什么属于确认前提

系统要求商品和规格曾在当前买家的当前会话中由检索返回。

模型正文写了一个商品名字或标识，不足以证明它已经被核对；目录中存在这个商品，也不足以证明用户看到过这个规格。

这个证据检查把推荐、用户选择和购买意向联系起来，减少模型交接时替换对象的风险。

### 18.4 数据库事务保证什么

事务把订单创建、明细保存、库存扣减和确认终态组织成一个提交过程。全部成功才提交，失败则撤销相关变化。

否则可能出现订单已经保存但库存没扣，或者库存扣了却没有订单。

批准时重新检查当前库存和报价条件，因为检索与批准之间可能发生其他交易。旧观察不能保证当前还能执行。

### 18.5 幂等为什么必要

用户双击、网络重试或队列重新投递，都可能导致同一操作多次到达。

幂等意味着同一项操作已经提交后，再收到相同决议应读取已有结果，不再创建第二个订单或再次扣库存。

若后续请求试图改变原来的决议，则应冲突，而不是改写已执行事实。取消同样要防止重复回补库存。

### 18.6 页面如何知道结果

页面根据持久确认终态和订单结果展示完成。事件推送失败，不改变已经提交的事务，刷新仍可恢复。

“批准”只是授权步骤，“完成”才是执行结果。这个区别适用于交易，也适用于记忆变更。

## 19. 权限护栏和故障保护

### 19.1 提示词为什么不能单独承担安全

模型可能忽略要求、误解工具结果，或受到外部文字诱导。只写“不要违规”并不能保证工具和交易合法。

项目将权限、身份、证据和事务作为执行边界，再用 Harness 补充过程约束。Harness 可以理解为围绕 Agent 的执行保障机制。

### 19.2 工具调用前后的检查

调用前检查前置条件，例如是否存在必要检索过程。调用中设置超时和熔断。调用后检查返回结构、重复程度和可能的外部指令注入。

这些检查通过中间件按顺序包住工具。没有通过准入检查的调用，不进入真正工具执行。

有些异常只是给模型纠错提示，让它下一步修正；明确不允许的写操作则拒绝。恢复后的会话不能仅因内存调用记录缺失被误判，最终仍要检查持久商品证据。

### 19.3 循环检测如何避免误伤

连续调用同名工具不一定是循环，正常翻页或修改条件也可能多次搜索。

项目同时比较工具参数、结果和状态。多次相同条件得到相同结果，才说明没有新进展，需要收敛提示。

这比只按工具名称计数更合理，但仍是过程启发式，不是自动证明任务完成。

### 19.4 为什么过滤工具结果中的指令

网页或商品描述可能夹带“忽略之前规则”之类内容。它们属于外部资料，而不是可信系统指令。

项目用模式检测替换常见注入片段，保留正常业务内容并留下过滤痕迹。最终文本还会对内部敏感信息模式做审核与脱敏。

模式检测有覆盖边界，不能当作完整语义安全证明。最终文本审核也不能被理解为所有此前已发送的增量都自动获得同样保护。

### 19.5 记忆审批为什么采用暂停和恢复

Agent 请求新增、修改或删除长期偏好时，权限机制产生待审批状态，暂停相应工具。

用户批准后，框架用专门确认事件恢复执行；拒绝则不修改。不能把普通用户文字“同意”伪装成这份确认事件。

审批后仍可能因目标版本变化而失败。因此页面必须区分等待、已批准和已完成。

### 19.6 超时和熔断的区别

超时限制一次工具等待多久；熔断根据连续故障决定是否暂时不再请求坏依赖。

熔断开启后快速返回不可用，过一段时间再有限探测是否恢复。这减少重复无效等待，也保护已经不稳定的服务。

### 19.7 请求预算怎样覆盖并行调用

整轮预算启用后，模型调用先预留预计输入和输出空间，结束后根据实际或可用估计结算。并发子任务共享同一账本，重试也要重新预留。

剩余预算下降时，可以切轻量模型、要求简洁回复，或停止模型调用，依据已经验证的结果给规则回复。

该能力默认关闭。单次回答变短不能控制整轮成本，所以请求预算与单次输出限制需要分别存在。

目标漂移检测也是可选能力。当前轮末报告能帮助发现问题，不表示它已经自动纠正了本轮回复。

## 20. 队列并发与旧状态保护

### 20.1 网页执行与队列执行是两条路径

当前网页通过持久运行组件在 API 服务进程中执行 Agent。

兼容的意图接口在配置了 Redis 并启用队列时，可以先入队，再由独立工作进程执行。开启队列不意味着网页任务自动转交工作进程。

两条路径共用应用编排和业务能力，执行位置与结果传输方式有所不同。

### 20.2 队列怎样削峰

请求同时到来时，队列暂存等待任务，工作进程只允许有限数量的任务同时执行。

因此削峰来自消费并发限制，接口是否立即返回并不是关键。同步接口也可以在任务入队后等待结果，异步接口则先返回任务标识。

不同体量任务可以分队列，降低长会话阻挡短请求的风险。

### 20.3 为什么队列会重新投递

任务领取后，工作进程可能崩溃，队列不能把“领取过”视作“已成功”。未确认任务会保留在等待确认区，由恢复机制重新领取。

这种模式保证至少一次处理机会，并不保证任务只执行一次。业务幂等和事务仍然必要。

无法完成的任务进入失败或死信处理，终态归档保留排查材料。清理不能只按队列长度粗暴删除还活跃的任务。

### 20.4 会话锁解决什么

同一会话两条请求同时修改模型工作状态，会造成消息交错或后保存者覆盖前保存者。

进程内锁先避免本进程的并发修改。跨进程时还需要租约，规定哪个执行者在一段时间内有权处理，并通过心跳续期。

### 20.5 为什么租约还不够

假设工作进程甲卡住，租约过期，乙接手完成了新工作。甲后来恢复，仍可能拿着旧状态尝试保存。

因此数据库保存时检查递增的执行权标识和预期版本，拒绝旧执行者或旧版本写入。这些机制通常称为 fencing 和比较后更新。

本地锁避免同时工作，租约决定当前执行者，数据库的版本与执行权检查负责最终拦截迟到写入。

### 20.6 跨进程事件为什么需要背板

一个进程里的本地事件订阅，不能直接听见另一个进程发布的业务事件。

Redis 事件背板把工作进程事件传给接口进程，再送到旧客户端通道。它适合跨进程实时通知，但不等同于持久运行日志，不能单独承担历史回放。

## 21. 启动存储和可观测性

### 21.1 装配中心为什么存在

系统启动需要确定各组件连接关系：哪个模型、哪个商品仓储、哪个交易账本、哪些工具、是否启用队列，以及各组件共享哪个限流器。

装配中心统一建立这些对象，使网页服务与工作进程使用相同连接方式。否则两个进程可能各自配置出不同规则和配额。

配置集中读取，运行时选择按轮次冻结，二者共同提高行为的可解释性。

### 21.2 初始化和关闭为何属于架构

启动还要建立必要存储、初始化库存、恢复运行日志、同步商品向量和加载知识索引。

某些可选检索能力失败，可以记录事实并降级；交易持久底座失败，不能改用临时内存却向用户声称已经可靠保存。

退出时要结束任务、关闭模型连接、释放数据库与向量库资源，并处理追踪导出。资源没释放，下一次启动可能遇到锁或连接问题。

### 21.3 为什么有多种持久存储

关系数据库擅长订单、库存、确认和版本关系；向量索引擅长语义相似检索；本地目录便于固定样例商品；Redis 适合共享缓存、队列和短期协调。

偏好、方案、表单、运行日志和证据也有独立存储职责。分开能够隔离模块，但备份与恢复要考虑多份数据之间的配套关系。

例如只备份订单而不保存确认记录，会丢失授权过程；保存模型数据库却丢失主密钥，会导致加密凭据不可读。

本地嵌入向量库还有目录进程锁。多个进程共用时通常需要服务型向量库，而不是删除现有数据来消除锁。

### 21.4 日志、追踪和指标怎样配合

日志记录具体事件和错误。分布式追踪把请求、Agent、模型、工具和队列步骤串起来，帮助找到慢在哪里。指标聚合调用量、故障率、延迟和消耗。

项目使用 OpenTelemetry，并可通过 OTLP 将追踪送到相应观测服务，例如 Langfuse。

它们回答不同问题：日志说明某一步发生了什么；追踪展示一轮经过哪些组件；指标观察一段时间的整体表现。

### 21.5 健康检查为什么不等于选购成功

服务正在运行、数据库能够查询，不代表模型凭据有效、精排可用或推荐符合需求。

即使真实模型成功返回一次，也不能证明所有场景的质量、安全、完整费用和延迟收益。

观察系统状态与验收业务效果必须分别进行，未知指标应明确写未知。

## 22. 评测离线学习与理解检查

### 22.1 不同验证回答不同问题

确定性测试验证身份、金额、版本、事务、协议和恢复规则。真实模型冒烟验证指定环境中的基本模型工具链路。冻结数据评测比较多个场景下的质量、约束和消耗。

上线门禁还要同时检查安全、完整实际用量和延迟。只看最终回复文本长度，可能遗漏子 Agent、失败重试、摘要和回退的消耗。

项目要求相关运行保障修改保留基线与新报告，并核对模型、网关、数据和版本。只挑容易场景、缺凭据或跳过安全契约，不能写成完整通过。

### 22.2 检索指标怎么理解

召回指标检查目标商品有没有进入候选；排序指标检查它排得是否靠前；硬约束指标检查超预算、不可配送等结果是否被正确排除。

知识库还需要检查没有答案时能否说明不足，以及政策资料是否具备有效来源和适用条件。

样例太少会让指标虚高。需要相近但不合适的商品、无法回答的问题和真实失败样本，才能区分不同方法。

### 22.3 离线学习怎样运作

项目提供默认关闭的学习采集能力。启用后，可以把符合条件的运行终态交给独立学习任务。

学习组件读取证据，保存失败诊断，或使用独立模型提炼可复用的方法候选。它没有在线交易或自动发布权限。

候选需要进一步验证、人工审核和精确内容核对，才允许显式发布。用于最终验收的保留数据不能偷偷参与学习。

这里沉淀的是文本策略，不是自动训练模型权重。模型自评成功只是筛选信号，不是已经证明方法有效。

### 22.4 商家沙箱和候选能力的边界

项目包含受限的本地商家协议沙箱，用于演示报价核验与审批。它没有让主页面自动连接真实支付或商家供给。

混合检索、分层上下文、显式提示词缓存和有限续写等候选，也要区分“已经实现”“已经启用”“已经通过效果验收”。这三个状态不能互相替代。

### 22.5 用这些问题检查是否理解

1. 用户说“第二个”时，为什么既要看历史候选顺序，又要核对当前库存？
2. 为什么商品卡的价格不能从模型回答文字里解析？
3. 向量搜索没有找到某商品，为什么不能直接断言商品不存在？
4. 为什么检索时有库存，批准购买时还要再检查？
5. 用户点击两次批准，哪个机制防止库存扣两次？
6. 为什么网络重连读取日志，而不是重新启动 Agent？
7. 一次用户输入为什么可能产生多次模型费用？
8. “这次要蓝色”和“记住我喜欢蓝色”为什么保存方式不同？
9. 为什么 Skill 可以改变处理方法，却不能免除交易批准？
10. 工作进程租约过期后恢复，为什么还要由数据库拒绝旧状态？
11. 模型窗口很大，为什么仍需输出预留、安全预留与工作目标？
12. 测试通过、真实链路成功和生产效果达标分别证明什么？

理解这个项目的关键，是能够沿着一个用户动作说明：输入由谁解释，事实由谁查询，权限由谁决定，状态由谁保存，故障由谁处理，以及最终结论有什么证据支持。
